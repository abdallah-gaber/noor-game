# ADR 007 — Android release signing

The direct-install release uses application ID `dev.noor.noor`, one dedicated PKCS#12 signing key and increasing Android version codes. Gradle requires a configured release key. Debug builds continue to use the Android development key. Keep the release key and its password outside the repository, artifacts and logs. Record the public SHA-256 certificate fingerprint in release evidence and compare every candidate against it.

On the release machine, the key file is restricted to the owner account and the password is stored separately in macOS Keychain. Release builds read `NOOR_RELEASE_STORE_FILE` (absolute path), `NOOR_RELEASE_STORE_PASSWORD` (store and key password), and `NOOR_RELEASE_KEY_ALIAS`. Use the same inputs for `flutter build apk --release` and `flutter build appbundle --release`. Verify the APK with `apksigner verify --print-certs` before distribution. Transfer the key to an owner-managed encrypted backup and verify restoration before relying on a second release machine.

Android accepts an in-place update only when the application ID and signing identity are compatible and the version code permits it. The previous debug-signed pilot is a separate signing lineage. Keep an existing pilot intact if Android rejects a release update. Any future Play distribution must preserve this app-signing identity for sideload continuity. A Play upload key serves a different purpose.
